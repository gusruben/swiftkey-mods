# geometry: Moopad ui-glue decisions, decoder-read fields, KeyboardModel

The port runs inside SwiftKey, which owns the keyboard UI and supplies its own key rects. This
file says which `Emkey::Moopad` "ui-glue" functions (inventory kind `ui-glue`) are decoder
logic, which are UI that the host replaces, and exactly which board fields the decoder reads.

Status as of 2026-10-20: every function marked **ported** passes its golden vectors bit for bit
(`re/vectors/gen_geometry*.py`, adapters in `ports/GeometryPorts.kt`).

## Coordinates (confirmed from the code)

- Board space = `touch / 2 - screenKeyboardOrigin()` on the reference setup, where
  `screenKeyboardOrigin() = (rect.left, rect.top - Moopad[0x1f498] + Moopad[0x1f4b8])` and
  `rect = Cns::getRectOnScreen()` in roen units. The /2 is the roen scale: RoenGL's width
  (RoenGL+0xb28) is 540 for the 1080-px surface. On the reference boot the origin is (0, 152):
  rect top 206, topbar height 54, extra 0. Measured: touch (300, 500) is recorded as (150, 98).
- The 152 is therefore not a magic number. It is the on-screen top of the letter rows (206)
  minus the topbar (54). Board y = 0 is the top of the topbar row (row 0, y 0..54). The QWERTY
  rows are 54..108, 108..162 and 162..216, and the spacebar row is 216..270. In touch space
  the keyboard spans y 304..844, which is why touch y runs past the 432-px surface.
- Key pitch is 54 = Moopad 0x1f4a0 (keyHeight = `curboardVertlen`) = 0x1f4a4 (keyWidth). The
  key-unit distance divisor is 0x1f4a8, also 54.

## KeyboardModel

`KeyboardModel.nintype()` rebuilds Nintype's own board from `NintypeLayout.kt`, which is
generated by `gen_geometry_board.py`. The file holds raw bytes of every decoder-read span of all
47 live keys, the board scalars, the Moopad layout fields, the tile map, the unicode index and
the named keys. Three vector files check it against the unmodified booted board: findKey on
3996 points, clampCoveragePos on 1500 points and findKeyByUnicode on 238 lookups. All three
match bit for bit.

`KeyboardModel.fromRects(keys, pitchXPx, pitchYPx)` builds a board from a host's labels and
pixel rects by running Nintype's own board-build path (`BoardBuild.kt`, every step
vector-verified; see "Board build" below) on them. The rects take the place of
Moorow::syncOrigKeyXes' worth layout; keys start from the Mookey() ctor defaults (so e.g. 0x54 =
-1: not an emoji-board key). Tested in
`src/test/kotlin/nintype/engine/geometry/KeyboardModelTest.kt`:

- Nintype's own letter and spacebar rows are redrawn as a host layout at 144 x 160 px per key
  with origin (37, 1800), then rebuilt with fromRects. The result equals Nintype's board up to
  the translation (0, 54); the host has no topbar row. Every key's rect, touch range, centre,
  row, label position, stair limit, type flags and tile set match bit for bit, and the spacebar
  is the named key 0xfac.
- findKey agrees on all 21,021 points of a 3-unit grid. The only exceptions are points on y = 54,
  where Nintype's topbar row also claims the point; the host has no topbar.
- clampCoveragePos is bit-exact on 15,000 points.
- findKeyByUnicode centres, unitDist between letter centres and getBiDirIndex for all 676 letter
  pairs are bit-exact.
- A plain staggered QWERTY (108 x 150 px keys) finds every key at its centre, catches edge
  touches, and puts keys 54 units apart.

### The mapping SwiftKey must apply

1. Pass each visible key: label, the code point it types (0 for function keys) and its pixel
   rect. Include the spacebar (chara 0x20), but not the suggestion strip.
2. Pass the key pitch per axis: `pitchXPx` = the letter-key width and `pitchYPx` = the row
   height, both in px. Each axis is scaled so one key is 54 x 54 units. All of Nintype's unit
   thresholds (unitDist, keyHeight-based slack, 0.3 * keyHeight, tile grid) assume square
   54-unit keys, so do not use one isotropic scale on a non-square layout.
3. Convert every touch with `model.toBoard(x, y) = ((x, y) - topLeftOfKeys) / (pitch / 54)`
   before it reaches the touch handler, and draw decoder output back with `toHost`. Nintype's
   own reference board uses `touch / 2 - (0, 152)` instead (see Coordinates).
4. These rules reproduce Nintype's own board:
   - Board (0, 0) is the top-left of the key bounding box, and rows are grouped by top edge.
   - Touch ranges come from Mookey::syncExpansions: a letter key with no previous (next) key in
     its row reaches 60 units past its edge, one next to a non-letter reaches to that key.
   - Each row's coverage clamp runs between its first and last slidable key (`HostKey.slidable`,
     Mookey 0xd49; default: types a chara or non-basic chara, spacebar excluded), the y clamp
     between the first and last row holding one (MooBoard::initionFinisher).
   - Tiles, the unicode / trie-char indexes (incl. upper case and non-basic charas), apostrophe
     keys and named keys come from the ported indexMookeyToMaplet, syncTrieCharKeys and
     syncNamedKeys. Pass `HostKey.typeName` ("space" is the default for U+0020; "caps",
     "backspace", "ret", "123", ...) for the keys syncNamedKeys looks up.
5. One Nintype quirk is opt-in: its shift key carries non-basic chara 'z', so slides over shift
   count as z, and getBiDirIndex for z uses both keys. Pass `nonbasic` on a HostKey to copy
   this. A plain SwiftKey shift leaves it 0.
